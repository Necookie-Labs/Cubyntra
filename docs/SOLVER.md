# Cubyntra Solver Specification

**Product**: Cubyntra  
**Organization**: Necookie Labs  
**Status**: Implemented (2.0.0)  
**Module**: `src/solver/`

---

## 1. Executive Summary

The solver is Herbert Kociemba's two-phase algorithm from the `rubik-solver` package, run in the browser without native binaries or server-side computation. It consumes a validated 54-facelet cube and produces a near-optimal sequence of face turns in Half Turn Metric (HTM).

In the tutor (2.0) its role is narrow: `confirmReview` in the scan store validates the scanned cube and solves it in the worker, and the result is kept in the scan store. **No tutor step comes from this solver**: every move the student is shown is planned by the deterministic tutor engine ([ADR-012](ADR/012-deterministic-tutor-engine.md), [METHODS.md](tutor/METHODS.md)), which also runs in this module's worker (§4.4). Timer scrambles come from `src/learn/scramble.ts`, not from `generateRandomScramble`.

## 2. Theoretical Foundation: Kociemba Two-Phase Algorithm

### 2.1 Group Theory & Subgroups
A standard $3 \times 3 \times 3$ Rubik's Cube has $43,252,003,274,489,856,000$ ($\approx 4.33 \times 10^{19}$) reachable states, generated by the group:
$$G = \langle U, D, R, L, F, B \rangle$$

Directly computing the shortest path to identity in $G$ via breadth-first search or $A^*$ requires prohibitive memory and time. Dr. Herbert Kociemba introduced the **Two-Phase Algorithm** (1992), which breaks the problem into two distinct coset spaces via an intermediate subgroup $H$:
$$H = \langle U, D, R^2, L^2, F^2, B^2 \rangle$$

In subgroup $H$:
1. All 12 edge orientations are correct (flip = 0).
2. All 8 corner orientations are correct (twist = 0).
3. The 4 middle-layer edges ($FR, FL, BL, BR$) remain within the middle layer ($UD$-slice).

### 2.2 Phase 1: Reduction to Subgroup $H$
- **Objective**: Transform any arbitrary cube state $S \in G$ into a state $S' \in H$.
- **Allowed Moves**: Any face turn from $\{U, U', U2, D, D', D2, R, R', R2, L, L', L2, F, F', F2, B, B', B2\}$.
- **Coordinates Evaluated**:
  - Edge Flip Coordinate: $2^{11} = 2,048$ states.
  - Corner Twist Coordinate: $3^7 = 2,187$ states.
  - Slice Permutation Coordinate: $\binom{12}{4} = 495$ combinations.
- **Search Strategy**: Iterative Deepening $A^*$ (IDA*) guided by precomputed pruning tables encoding minimum moves to reach $H$. Typically requires 7 to 12 moves.

### 2.3 Phase 2: Solving Subgroup $H$
- **Objective**: Transform $S' \in H$ to the identity (solved) state.
- **Allowed Moves**: Restricted exclusively to $\{U, U', U2, D, D', D2, R2, L2, F2, B2\}$. This invariant ensures orientations and slice membership are never broken.
- **Coordinates Evaluated**:
  - Corner Permutation Coordinate: $8! = 40,320$ states.
  - Edge Permutation Coordinate (Phase 2): $8! \times 4! = 967,680$ states.
- **Search Strategy**: Fast IDA* search restricted to $H$. Typically requires 10 to 14 moves.

### 2.4 Optimality & God's Number
- **God's Number** for the $3 \times 3 \times 3$ Rubik's Cube in Half Turn Metric is exactly **20 moves** (proven by Rokicki, Kociemba, Davidson, and Dethridge in 2010).
- Pure optimal solvers (e.g., Korf's optimal IDA*) require gigabytes of precomputed pattern databases and can take minutes to solve single positions on desktop hardware.
- The Two-Phase algorithm produces solutions averaging **21-23 moves** in under **50 milliseconds** on modern JavaScript engines, achieving the optimal balance between human speed and algorithmic efficiency.

## 3. Metric & Notation

Cubyntra strictly adheres to the standard World Cube Association (WCA) Half Turn Metric (HTM):

| Face | Clockwise ($+90^\circ$) | Counter-Clockwise ($-90^\circ$) | Half Turn ($180^\circ$) |
|:---:|:---:|:---:|:---:|
| Up ($+Y$) | `U` | `U'` | `U2` |
| Down ($-Y$) | `D` | `D'` | `D2` |
| Front ($+Z$) | `F` | `F'` | `F2` |
| Back ($-Z$) | `B` | `B'` | `B2` |
| Left ($-X$) | `L` | `L'` | `L2` |
| Right ($+X$) | `R` | `R'` | `R2` |

### Move Inversion
To reverse a move sequence during playback or undo operations:
$$(A \cdot B)^{-1} = B^{-1} \cdot A^{-1}$$
Individual move inverses:
- `U` $\leftrightarrow$ `U'`
- `U2` $\leftrightarrow$ `U2`

## 4. Implementation Architecture

### 4.1 Module Structure
```
src/solver/
├── types.ts          # SolveResult
├── solver.ts         # solveCube(), ensureSolverInitialized(), generateRandomScramble()
├── protocol.ts       # WorkerJobs: the typed message protocol for the worker
├── handlers.ts       # the work behind each message type; dispatch()
├── solver.worker.ts  # Web Worker entry point
└── client.ts         # SolverClient, solveInWorker(), warmUpSolver()
```

### 4.2 Facelet Mapping
The solver accepts a 54-character string with indices 0–53 ordered by facelet conventions:
```
             +------------+
             | U1  U2  U3 |
             | U4  U5  U6 |
             | U7  U8  U9 |
+------------+------------+------------+------------+
| L1  L2  L3 | F1  F2  F3 | R1  R2  R3 | B1  B2  B3 |
| L4  L5  L6 | F4  F5  F6 | R4  R5  R6 | B4  B5  B6 |
| L7  L8  L9 | F7  F8  F9 | R7  R8  R9 | B7  B8  B9 |
+------------+------------+------------+------------+
             | D1  D2  D3 |
             | D4  D5  D6 |
             | D7  D8  D9 |
             |------------+
```

### 4.3 Simulation & Solution Verification
Cubyntra implements a mathematical verification engine in `src/solver/solver.ts`:
1. `solveCube(state)` rejects a state that fails `validateCubeState`, and returns no moves for a solved cube.
2. It turns the state to standard orientation (`normalizeOrientation`), serializes it with `cubeStateToFaceletString` and runs the two-phase search.
3. The solution is parsed (`parseAlgorithm`), translated back into the frame the cube is held in, and applied to the original state with `applyMoves`.
4. Unless `isCubeSolved` holds for the result, the solve is returned as `success: false` with an error.

### 4.4 Web Worker
Building the Kociemba tables takes a few seconds and a search can take tens of milliseconds, so
both run in a Web Worker and the 3D twin never stutters.

- **Bundling**: `client.ts` creates the worker with
  `new Worker(new URL('./solver.worker.ts', import.meta.url), { type: 'module' })`, the form
  Turbopack and webpack both recognize and emit as a separate worker chunk.
- **Protocol** (`protocol.ts`): every request is `{ id, type, ...payload }` and every reply
  `{ id, type, ok: true, result }` or `{ id, type, ok: false, error }`. `WorkerJobs` maps each
  `type` to its payload and result:

  | `type` | payload | result |
  |---|---|---|
  | `init` | none | `{ ready: true }` (tables built) |
  | `solve` | `{ state: CubeState }` | `SolveResult` |
  | `tutor.plan` | `{ state, method, grip?, stepIndex?, options? }` | `StepPlan \| null` (`planNextStep`; null when solved) |
  | `tutor.progress` | `{ state, method, options? }` | `TutorProgress` |
  | `tutor.guidedSolve` | `{ state, method, grip?, options? }` | `GuidedSolve` (`runGuidedSolve`) |

  The tutor jobs call the tutor engine (`src/tutor/`, [METHODS.md](tutor/METHODS.md)); a
  `TutorPlanError` becomes an `ok: false` reply. Step plans are plain data (states, moves,
  grips, strings), so they cross the boundary unchanged. Shortcuts: `planStepInWorker`,
  `tutorProgressInWorker`, `guidedSolveInWorker`.

  New jobs are an entry in `WorkerJobs` plus a handler in
  `handlers.ts`; the client is typed from the same map
  (`client.request(type, payload): Promise<result>`). Everything crossing the boundary is plain,
  structured-cloneable data.
- **Errors**: `dispatch()` never throws; a handler error becomes an `ok: false` reply and the
  client rejects with that message.
- **Fallback**: where `Worker` is undefined (tests, server rendering) or the worker fails to load
  (`error` / `messageerror`), the client runs the same handlers on the main thread, re-running any
  request that was waiting.
- **Use**: the scan store solves with `solveInWorker(state)`; the tutor store plans with
  `planStepInWorker`, and Home reads progress with `tutorProgressInWorker`. `warmUpSolver()` is
  exported but nothing calls it at present, so the first scan builds the tables.

`tests/solver-worker.test.ts` covers the handlers, the worker entry point, the client with a fake
worker (concurrent replies matched by id, errors, fallback after a crash) and the main-thread
fallback; `tests/tutor-worker.test.ts` covers the tutor jobs (same plans as the engine, structured
clone both ways, errors, fallback); `tests/store-solver-client.test.ts` checks the store goes through the client.

## 5. Performance

No benchmark is part of the test suite, so this document gives no timing figures. What is tested
(`tests/solver.test.ts`): a solved cube gives 0 moves; a short scramble, a medium scramble (Sune
plus J-perm) and a random scramble are solved and the result verified solved; an invalid cube is
rejected before the search. Kociemba solutions are typically 18–22 HTM moves; the tutor's guided
solves are much longer by design ([METHODS.md](tutor/METHODS.md) §8.1: 155.8 turns on average for
the beginner's method, 75.7 for CFOP 2-look).

## 6. Error Handling & Edge Cases

1. **Invalid cube**: `solveCube` returns `success: false` with the validator's messages. The
   validator's issue codes include `INVALID_COLOR_COUNT`, `INVALID_CENTERS`,
   `INVALID_CORNER_COLORS`, `INVALID_EDGE_COLORS`, `CORNER_TWIST_PARITY`, `EDGE_FLIP_PARITY`
   and `PERMUTATION_PARITY`.
2. **Unreachable orientation or a search failure**: returned as `success: false` with the error
   message; the scan store shows the error state.
3. **No timeout**: the search is not time-limited; it runs in the worker, so a slow search does
   not block the page.
